# CLAUDE.md — ae3.sys.pkg.l2.tgt.xls

AE3 L2 media target for MS Excel (`.xls`) output, built on JExcelAPI (`jxl.*` via `ru.myx.util.xls.ExcelSAPI`).

## Two unrelated things both called "xls" here — don't conflate them

- `java/ru/myx/ae3/l2/xls/XlsFileTargetContext.java` — a trivial `NativeTargetContext` (`TargetMode.CLONE`) debug dumper: writes whatever raw layout object it's given as generic XML text to a file. Not real Excel output, not part of the layout-engine walk, not related to anything else in this file.
- `ae3-packages/ae3.sys.l2.tgt.xls/resources/lib/ae3/xls.js` — **not a layout-engine generator, and its independence from `TargetContextAbstract` isn't a gap** - it's a static SAPI-style module (`ExcelSAPI`-based) exposing a programmatic API for scripts to call directly (`makeDataTableReply`/`makeDataTableBinary` for `{columns, rows}`-shaped layouts: real per-column formatting, fonts, hyperlinks, merged title cells). `ae3.sys.pkg.base` has many of these (most far less optional than this one); the pattern is deliberate - XLS support is either installed (JExcelAPI/`jxl.jar` present) or not, so keeping it as an independently-loadable script rather than baking it into the layout-engine registration avoids coupling the walk to an optional external dependency. The actual bug some callers hit: `ae3.sys.pkg.l2.tgt.xml`'s `Make*ReplyFn.js` helpers used to call `require("ae3/xls").makeDataViewReply(...)` - a method this script never exported (its real exports are `makeDataTableReply`/`makeFormReply`, not `makeDataViewReply`) - a caller-side name mismatch, not a missing module.

  Three real bugs found and fixed this session, all copy-paste artifacts shared with this script's siblings (`ae3.sys.pkg.l2.tgt.pdf`'s `pdf.js`, `ae3.sys.pkg.l2.tgt.html`'s `html.js` - same defects found and fixed identically in both, same session):
  - `createBinaryFromLayout` referenced `new XlsReplyTargetContext(query, null, null)` - a class that never existed (word-order-swapped from `pdf.js`'s working `PdfTargetReplyContext`, which *does* exist - see its own `CLAUDE.md`). Fixed by adding the missing `XlsTargetReplyContext` class (mirrors `PdfTargetReplyContext` exactly: a self-contained context a script constructs directly with a layout + `ServeRequest`, sending its own reply from `doFinish()`) and correcting the reference plus the two missing `import`s (`SimpleServeRequest`, `XlsTargetReplyContext`) this function always needed.
  - `makeDataTableReply`/`makeFormReply`/`makeDataTableMessage`/`makeFormMessage` all referenced a bare `name` that was never defined in their scope (only `layout.name` exists, and only inside a *different* function, `makeDataTableBinary`/`makeFormBinary`). Fixed with `const name = layout.name || 'data';` in each. Note for future editors: don't "improve" this into template literals or an extracted-and-reused constant - asked for and rejected twice this session; keep matching this file's own existing plain-concatenation style.
  - `makeFormBinary` (the variant closer to a `{fields, values}` single-record shape) still has a real, separate, **not yet fixed** bug: it references `columns`/`columnCount`, which are never defined in that function — a copy-paste artifact from `makeDataTableBinary`.

## Build

- Requires (Java, AE3-internal, confirmed by source imports): `ae3.sdk` — cross-package imports resolve to `ru.myx.ae3.base.BaseMessage`/`ru.myx.ae3.i3.TargetInterface` (`ae3.api`) or `ru.myx.ae3.binary.*`/`ru.myx.ae3.l2.*`/`ru.myx.ae3.xml.Xml` (`ae3.sdk`).
- Also requires `clean-java.io` (a separate, non-`A-E-3`-org repo under GitHub user `myx` — `myx/clean-java.io`) for `ru.myx.io.DataInputByteArrayFast` — that repo's `project.inf` (`Type: ae3.Package`, `Title:` instead of `Info:`, a slightly different dialect) `Provides: clean-java.io` matches its own `Name:`. Wired into both `project.inf` `Requires:` and `.classpath`.
- **JExcelAPI (`jxl.*`)** — from `lib.jexcelapi-jxl` (Eclipse project name `ae3.pkg.lib.jxl`) under `source/lib`. Same wiring pattern as `ae3.sys.pkg.l2.tgt.pdf`'s iText dependency: a `kind="src"` `.classpath` entry to `/ae3.pkg.lib.jxl` plus a `kind="lib"` entry for `jxl-2.6.12.jar`; `project.inf` `Requires:` doesn't list it (same as iText — jar deps are `.classpath`-only in this build system).
- `package.json`: two bundles — `ae3.sys.l2.tgt.xls` (main) and `ae3.sys.l2.tgt.xls-docs` (`"requires": ["ae3.web", "ae3.manual"]`, documentation-specific — same pattern as `ae3.sys.pkg.l2.tgt.pdf`'s `-docs` sub-bundle).

## New this session: a real, walk-integrated XLS engine, added 2026-07-17

Added `XlsTargetContext`/`WebContextXls`/`XlsLayoutString`/`XlsLayoutGrid`/`XlsLayoutDefinition`/`XlsElement`/`XlsElementGrid`, mirroring `ae3.sys.pkg.l2.tgt.pdf`'s pattern (`PdfTargetContext`/`PdfElement`/`PdfElementGrid`/`current`/`onLeave` → `doFinishAndGetParent`) as closely as the underlying library allows, plus `settings/system/l3/targets/xls.json` (registers `WebContextXls` for the `xls` extension/keyword, same shape as `pdf.json`) — `xls` is now a real, selectable output target for the first time, not just this unit's standalone script.

**One necessary, real divergence from the PDF pattern, not a shortcut**: iText's `PdfPTable` understands column counts natively and auto-wraps rows once cells are added sequentially, so `PdfElementGrid` needs no coordinate bookkeeping. JExcelAPI has no equivalent — every cell needs an explicit `(x, y)` — so `XlsElementGrid` computes row/column from a running index instead, and `XlsTargetContext.reserveRows(count)` atomically reserves row space for a grid so a sibling element after it can't collide.

**Deliberately minimal ("basic layouts... map elements to what the library understands")**: only `string`/`grid` are registered — no `link`/`container`/`image`/`numbered` the way PDF/HTML have, no per-column type inference (dates, currency, hyperlinks — the way `ae3/xls.js`'s `formatterDate`/`formatterInteger`/`formatterHref` do). Every cell is written as a plain text label via `WorkbookCellFormat` from `createCellFormatText()`. `ae3.sys.pkg.l2.tgt.xml`'s `ReduceDataViewGridXlsFn.js` (parallel to its pdf/txt/html siblings) folds the `link` field variant into inline text for the same reason text's version does — no native link cell type exists here yet.

**Verified against two independent live examples during design, not guessed from one file in isolation** — cross-checked the pattern across `ae3.sys.pkg.l2.tgt.html`'s `HtmlLayoutHtmlTr`/`HtmlLayoutHtmlTd`/`HtmlContextHandler` (DOM-tree row/cell variant) and `ae3.sys.pkg.l2.tgt.pdf`'s `PdfElementGrid`/`PdfElementSequence`/`PdfContextHandler` (iText variant) together before writing anything, per an explicit ask not to generalize from a single unit. Also checked `about.jsld` (`{layout:"intl", value:{en,ru}}`, present in every `l2.tgt.*` unit) and `skin-failover/layouts/Intl.jslt` (`return layout.value.en;`) as a second, independent, pre-existing confirmation of the same "reduce to a universal primitive, let each format's own real engine finish it" design already established in this codebase — not a pattern invented for this session's `data-view` work.

**Not compiled or run** — no way to do that from here. Everything above is a careful, cross-referenced static design, following established precedent as closely as the library differences allow, but still unverified against a real build.

## Gotchas

- `WorkbookChange.buildWorkbook()` (via `ExcelSAPI`) must be called exactly once, **after** the walk (`transform()`) fully completes — see `XlsTargetContext.buildWorkbook()`'s own comment. Unlike PDF's streaming `PdfWriter` (which writes incrementally as elements are added), JExcelAPI's `WritableWorkbook` builds entirely in memory and only serializes on `write()`/`close()`. Calling it from `doFinish()` (mid-walk-lifecycle) instead of from `WebContextXls.getResultReply()` (after) would be a real, live-breaking mistake — don't move it there without re-checking this.
- `XlsTargetContext` is its own `XlsElement` root sink (`implements XlsElement` directly) rather than a separate `XlsElementDocument`-style class the way PDF splits `PdfTargetContext`/`PdfElementDocument` — there's no equivalent "document" object in JExcelAPI's model worth splitting out separately for this.
- **`.gitignore`'s `*.jar` rule may be wrong for this unit specifically** — same caveat as `ae3.sys.pkg.l2.tgt.pdf`: if JExcelAPI ever gets vendored into a `lib/` folder here, a blanket `*.jar` ignore would silently exclude it.
- 7 compiled `.class` files are checked into git under `bin/` — not yet cleaned up.
- See `ae3.sys.pkg.l2.tgt.html`'s CLAUDE.md for why `l2.tgt.xml`'s three-entry `Provides:` shape isn't treated as a confirmed convention here.
